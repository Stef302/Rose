## 1. Objectif et point de départ

Le banc global (`bench/global/bench_global.rose`) décompose l'exécution en
9 phases. Déjà intégrés **avant** R8 (RC5, non retirés) : réserve 8 192

Mission : trouver **UNE** optimisation restante sur tables (~327 µs) ou RNG
(~168 µs, ~75 % de défauts de page), la mesurer en A/A/A c6+c16 apparié, et
prouver le plancher si aucune n'est disponible.

## 2. L'optimisation retenue (UNE, 4 lignes)

**`Table::reindexer()` : ne pas refaire le `fill(0)` de `array_part` quand
`items` est vide.**

`Table::neuf(Vec::new())` (le `$tab = table()` du banc) construit un
`TableRep` neuf dont `array_part` sort **déjà zéro** de `vec![0u32; 4096]`
(16 Kio). Il appelait ensuite `reindexer()`, dont le seul travail réel sur
une table vide est un second `memset` de ces 16 Kio — soit 4 pages neuves
faûtées pour rien, sur un tableau qui ne sert qu'aux clés i64 denses
(les clés du banc sont des chaînes, `k_table → None`, donc `array_part`
n'est jamais lu).

```rust
if !items.is_empty() { array_part.fill(0); }
```

Aucun effet sémantique : avec des `items`, le refill reste exécuté ; les
trois `clear()` et la boucle d'indexation sur des structures vides sont des
no-ops. Aucun chemin de recherche n'est modifié.

### Candidats évalués et rejetés

| Candidat | Mesure / analyse | Verdict |
|---|---|---|
| Finaliseur d'avalanche dans `IndexRapide` (hash `h & 8191`) | Simulation sur `k1…k5000` : sonde moyenne **0,598** (max 22) en brut, **0,842** (max 53) en mixé → le finaliseur **aggrave** la dispersion | rejeté sans build |
| Garder l'appel mais sauter `reindexer()` dans `neuf()` (variante 1) | tables −9,8 µs mais **RNG +8,3 µs** (effet de placement LTO), total −1,5 µs | rejeté (wash) |
| `array_part` paresseux sur 6 chemins (déjà tenté en RC5) | gain du même ordre, +complexité sur 6 sites | non repris (ce garde suffit) |
| Pré-fault / THP sur le tampon RNG | voir §4 — plancher | prouvé impossible ici |

## 4. Plancher RNG — preuve renforcée

Le micro-jumeau `/tmp/opencode/r8_agents/rng_warm.rose` appelle
`remplir_hasard` **trois fois sur le même tampon de 10⁶ octets** (le vrai
code, pas un jumeau approximatif) :

```
1er remplissage (pages neuves) : 174 127 … 258 400 ns   (médiane 210 608)
2e  remplissage (mêmes pages)  : 40 640 … 41 072 ns
3e  remplissage (mêmes pages)  : 40 640 … 40 752 ns
```

Le coût irréductible de calcul est donc **~40,7 µs**, stable à ±1 % même
sous charge ; les **~170 à 220 µs restants sont des défauts de page noyau**
(256 pages de 4 Kio, ~880 ns/fault), pas du calcul.

| Voie | Résultat mesuré | Verdict |
|---|---|---|
| THP | `/sys/kernel/mm/transparent_hugepage/enabled` = `always madvise [never]` → **never** actif, `AnonHugePages: 0 kB` | indisponible |
| Hugepages explicites | `HugePages_Total: 0`, `nr_hugepages=0`, `Hugepagesize: 2048 kB` | indisponible |
| `MAP_POPULATE` / pré-touch (`fault_test.rs`, 9 échantillons) | préfault + remplissage ≥ remplissage seul : le pré-fault **déplace** le coût, ne le supprime pas | sans gain |
| Parallélisme 2/4/8 threads (RC5, sortie bit-identique) | +16 % à +71 % (`thread::scope` > gain de défauts) | plus lent |
| Réutilisation du buffer entre appels | `bench_global.rose:56` n'appelle `tampon(1000000)` **qu'une fois** par processus ; chaque mesure est un processus neuf | non applicable |
| Réduction des copies dans `remplir_hasard` | voie NEON `vqtbl4q_u8` déjà 16 octets/store, sortie bit-à-bit figée par les oracles | plancher de calcul |

**Conclusion RNG : plancher atteint et prouvé dans `run.rs`.** Aucune des
quatre voies proposées n'est applicable sur cette machine ; le candidat
final laisse la phase RNG inchangée (−64 ns, dans le bruit).

## 5. Plancher tables — ce qui reste hors périmètre

- La clé du banc est construite dans `interp.rs:3139`
  (`Valeur::s(format!("{}{}", prefixe, i))`) : c'est une feuille `PleinCourt`
  (≤ 16 octets ASCII), donc `octets_empruntes()` est `Some` et **aucun
  `aplatir()` n'alloue** dans `h()` ni `egale_rep()` (vérifié source).
- L'insertion pure (`inserer`) est **sans allocation** : un seul
  `rep_mut_nv()`, un seul hachage, `items.push` sur arène réservée,
  `IndexRapide` à 8 192 sans réhashage (5 000/8 192 = 61 % < 70 %).
- Le gros du restant est la construction de clé (`format!` ~123 µs,
  `Valeur::s`/`ChaineRep::plein` ~67 µs sur ~190 µs, mesure RC5) dans
  **interp.rs**, hors du fichier possédé. Le gain de ce document porte
  uniquement sur les 16 Kio de `array_part` inutilement réécrits.
